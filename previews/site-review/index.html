P1 - Confirmed visual issue - React Chamber

Claims headings overlap on phones

At 390 px, the React Claims table still fits too many columns into the available width. Headings overlap and country, owner and processing text break into fragments. A page-width check passes because the content is squeezed inside the viewport; the screenshot exposes the readability problem.

Proposal: use the Vue mobile pattern: Claim / holder, Next action and an accessible View action. Keep all fields in the opened record and the full desktop table. Compact padding alone will not solve this.

P1 - Confirmed markup issues - React

Correct clickable-row and metric semantics

The scan flags aria-expanded on ordinary table rows and generic dashboard rows. These elements do not support the state in their current roles. The Chamber performance metric list also has helper text outside the permitted definition-list structure.

Proposal: keep the real View / Review controls keyboard accessible; expose menu state on an appropriate menu button instead of ordinary rows. Retain row clicking and right-click actions. Put metric supporting text inside its corresponding description. Verify keyboard and screen-reader behaviour afterwards.

Needs manual investigation: React also produces focusable, hidden Tabster sentinels. These are generated focus-management elements; the scan alone does not establish a user-facing failure. Do not remove them blindly. Both versions have a named Quick access container without a supporting role; give the grouping appropriate semantics.

Observed rules: aria-allowed-attr, aria-conditional-attr, definition-list. Related name/role/state and structure checks remain part of the accessibility follow-up.

P1 · Confirmed behaviour · Vue Exporter

Selecting an uploaded document replaces the Carnet

In Setup, selecting Uploaded document while ATA Carnet is selected leaves only Uploaded document selected. React’s Carnet setup explicitly allows a Carnet with an uploaded document. This is a mismatch in the document choices, separate from adding a supporting PDF.

Proposal: preserve both selections for the permitted combination, keep the Carnet steps and verify the preview and submission payload. Do not change other document-combination rules.

Source: vue/editor.js, choose(doc). Reproduced by clicking the document button in a fresh sample draft; no application was submitted.

P2 · Confirmed visible text · Vue Chamber

Finish the remaining interface translations

The Arabic Applications view still shows interface labels such as Reference / exporter and Unassigned in English. Exporter names, references and product names are expected to retain their entered values.

Proposal: translate the remaining labels and plural forms, then check all six languages with long names, open filters and validation errors. The current pass confirms examples; it is not a native-speaker review of every translation.

P2 · Design consistency · Both versions

Use one compact row pattern

Applications, Claims, Stored Data and Reports use different cell padding, reference-button heights and action spacing. The proposed layout centres headings and values and reduces padding while retaining all information.

Preview result: Vue Exporter rows average 98 → 59 px; React Chamber rows 75 → 61 px; Claims about 99–105 → 76–77 px. React Exporter rows retain three lines of reference information and reduce more modestly, 96 → 88 px. These are sampled row heights, not claims about processing speed.

Keep icon hit areas usable and allow longer content to increase row height. Forcing every record to an identical height would hide information or create overlap.

P2 · Design proposal · Chamber

Give the document more room during review

At the reviewed desktop width, the file list, document pane and Application details share the same row. The preview toolbar wraps onto several lines and the document occupies a narrow central area.

Proposal: make the file list a compact Files control, allow Application details to collapse, and remember Fit width / Fit page. Keep Approve and Reject visible and preserve entered information when switching files. Keep the application checklist removed, as requested.

This is a proposed improvement to reading comfort; the review does not establish faster processing times.

P3 · Optional design refinement · Chamber

Put the next task ahead of statistics for processing staff

The Chamber dashboard places User Performance above the review queue, with Needs attention below it. This is useful for supervision, but operational users may benefit from seeing their assigned and urgent work first.

Proposal: offer a remembered task-first arrangement. Keep the existing reporting view and the Exporter’s Stats / Announcements choice. Test with users before changing the default.

Code, loading and scrolling

P2 · Load the selected language when it is needed

Both English workspaces loaded the Dutch, Swedish, Portuguese and combined other-language bundles: about 2.37 MB of decoded JavaScript before supplements. This is browser resource size, not compressed transfer size or a measured startup delay.

Load the selected language first and load other dictionaries on demand. Measure cold-load performance on a slower connection before and after.

P2 · Consolidate the shared table styling

React’s entry page includes 38 stylesheets; Vue includes eight. The count alone is not a defect, but repeated table overrides make consistent changes harder. Introduce shared spacing, badge and action-size rules, with explicit exceptions for dense forms and mobile tables.

P2 · Make Vue’s editable lists and saving easier to maintain

Some repeated form rows, including trips in vue/editor.js, have no stable key. Use record IDs for mutable rows and test deleting or copying a middle row while another field has focus. Vue recommends keys where child or form state matters. This is a source-level risk; data loss was not reproduced.

vue/app.js watches records and interface state deeply and serializes them together. Separate frequently changing display preferences from application saves, retain save-error feedback and flush pending saves when leaving the editor. Test large sample queues before claiming a performance improvement. Keep browser-only storage, as requested.

Lenis: retain native scrolling for now

No Lenis runtime was found in the application. Its documentation was used to review the scrolling approach; it was not installed. These are forms and document workspaces with independent scrolling panes. Adding smooth scrolling is not needed to resolve the observed issues. Keep keyboard scrolling, nested PDF panes and reduced-motion behaviour intact.

Evidence and limits

This is not a WCAG conformance certificate. Automated scans cover selected rules and states. Keyboard-only end-to-end tasks, screen-reader use, 200% text resize, 320 px reflow, print output, PDF stamping gestures and every translation still require dedicated checks. W3C describes a broader conformance evaluation process.

No automated colour-contrast violation was reported in the scanned states. That result does not cover every hover, focus, error or document state.

Automated results: 36 scans, 12 pages with reported violations; 0 failed evidence/check cases. Items returned as “incomplete” need manual review and are not automatically failures. Do not treat a 32 px icon button as a WCAG size failure solely because it is below 44 px: WCAG 2.2 AA uses a 24 px minimum with exceptions.
